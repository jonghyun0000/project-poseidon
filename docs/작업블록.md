# 작업 블록 — 한 번에 하나씩 넘기는 요청 양식

규칙은 루트의 `AGENTS.md`에 있다(`CLAUDE.md`는 그것을 불러오기만 한다). 에이전트든 사람이든 규칙 파일을 먼저
읽게 하고, 요청은 아래 **작업 블록만 채워서** 넘긴다. 다음 할 일 후보는 `HANDOFF.md` §5에 우선순위대로 있다.

---

## 빈 양식 (이걸 채워 쓴다)

```
## 이번 작업

목표
  (한 문장. 무엇이 되면 끝인지)

왜
  (해운 항로 시뮬레이션에서 이게 왜 필요한지 한두 줄. 이유가 안 써지면 아직 할 일이 아니다)

범위 — 건드려도 되는 파일
  (경로를 명시. 안 쓰면 온 저장소를 헤집는다)

건드리지 말 것
  (특히 검증된 엔진·게이트 테스트)

완료 조건
  (숫자나 관측 가능한 상태로. "잘 되면"은 완료 조건이 아니다)

먼저 할 것
  구현 전에 계획과 예상 변경 파일 목록을 보여주고 승인받을 것
```

## 예시 1 — 대시보드를 해운 실무 수준으로 — **[완료: PHASE18]**

```
## 이번 작업

목표
  web/public/index.html(352줄 임시 프로토타입)을 해운 실무자가 운항 판단에 쓸 수 있는
  화면으로 올린다.

왜
  현재 화면은 파고를 turbo 컬러맵으로 예쁘게 칠할 뿐, "이 항로로 지금 나가도 되는가"에
  답하지 못한다. 해운 용도의 첫 관문은 운항 가부 판단이다.

범위 — 건드려도 되는 파일
  web/public/index.html
  poseidon/api/app.py 의 /v1/field/* 엔드포인트

건드리지 말 것
  엔진(engines/), 검증(validation/), 수집(ingest/), 스케줄러(scheduler/)

요구 사항
  1. 파고 색을 연속 컬러맵이 아니라 운항 판단 임계로 구분한다.
     임계값은 문헌이나 해운 실무 기준을 찾아 근거를 남기고, 못 찾으면 [확인 필요]로 표기한 뒤
     가안(예: 2.0 / 3.0 / 4.0 m)으로 두고 상수 한 곳에서 바꿀 수 있게 한다.
  2. 지점 예보 표에 리드별 등급을 함께 표시한다.
  3. 시간 애니메이션 재생·정지 버튼 (현재는 슬라이더 수동 조작뿐).
  4. 화면 어딘가에 데이터 기준 시각과 사이클 나이를 항상 노출한다.

완료 조건
  서버 재시작 후 브라우저에서 4개 항목이 실제로 동작하는 것을 확인하고 스크린숏으로 보고.
  기존 API 계약(integration 테스트 4종)이 깨지지 않을 것.

먼저 할 것
  구현 전에 화면 시안(단일 HTML)을 보여주고 승인받을 것.
```

## 예시 2 — 파주기·파향을 예보에 저장 (해운의 전제조건) — **[완료: PHASE13]**

```
## 이번 작업

목표
  예보 zarr에 유의파주기와 평균파향을 hs와 함께 저장하고, 점 예보 API에 노출한다.

왜
  선박이 받는 하중은 파고 단독이 아니라 주기와 상대파향(선수파/횡파/추파)의 함수다.
  현재 예보 변수는 hs 하나뿐이라 항로 시뮬레이션이 원리적으로 불가능하다.
  엔진은 이미 스펙트럼 E(f,θ)를 다 풀고 있고, 저장할 때 버리고 있을 뿐이다.

범위 — 건드려도 되는 파일
  poseidon/engines/spectral_wave/regional.py   (스펙트럼 적분 진단량)
  poseidon/scheduler/wave_cycle.py             (L1 저장부)
  poseidon/scheduler/nested_cycle.py           (L2 저장부)
  poseidon/api/app.py                          (forecast_point 응답)
  docs/api/openapi.yaml, docs/PHASE7_PREDICTION_ENGINE.md
  tests/unit/

건드리지 말 것
  소스항(sources.py), 이류·굴절 스킴, 보정 상수 CAL_*.
  이번 작업은 저장·노출만이다. 물리는 손대지 않는다.
  docs/ENGINE_FREEZE.md의 동결을 깨지 않는다 — 저장부만 건드리므로 동결 위반이 아니다.
  위반이 된다고 판단되면 진행하지 말고 먼저 보고할 것.

기존 배관 활용
  zarr attrs에 이미 advection·gse·gse_gamma·produced_at이 기록되고 collocate가 그것을
  features로 전재한다(2026-08-23). 새 변수도 같은 경로를 따르게 하고, 별도 배관을 만들지 않는다.

요구 사항
  1. 적분 정의(Tm01/Tm02/Tp 중 무엇, 평균파향의 규약이 from인지 toward인지)를
     WAM/WW3 관행 문헌으로 명시하고 코드 주석과 문서에 근거를 남긴다.
     PHASE6 §12에 DIRPW 방향 규약 오독 리스크가 이미 기록돼 있으니 그것부터 확인할 것.
  2. 기존 hs 값이 비트 단위로 불변임을 테스트로 증명한다.
  3. fp32 JAX 경로에서 에너지 0 셀의 진단량이 NaN이 되지 않는지 확인한다 (PHASE9 §2 사례).

완료 조건
  사이클 1개를 재실행해 zarr에 변수 3개가 들어가고, 단위 테스트 통과,
  경계 원천인 GFS-Wave의 perpw·dirpw와 교차 비교 지표(상관·편향)를 표로 보고.

먼저 할 것
  구현 전에 어떤 적분량을 쓸지와 그 문헌 근거를 먼저 제시하고 승인받을 것.
```

## 예시 3 — 리드타임 72시간 확장 — **[완료: PHASE12 §3.2]**

```
## 이번 작업

목표
  파랑 예보 리드를 24시간에서 72시간으로 늘리고, 어느 리드부터 성적이 무너지는지 밝힌다.

왜
  해운 항차는 짧아도 3일이다. 부산-상하이도 30시간이라 24시간으로는 한 항차를 못 덮는다.
  리드타임은 해운 용도 성립 여부를 가르는 첫 번째 숫자다.

범위 — 건드려도 되는 파일
  poseidon/scheduler/wave_cycle.py, nested_cycle.py
  poseidon/scheduler/ingest_cycle.py (강제장 스텝 수)
  docs/PHASE7_PREDICTION_ENGINE.md

건드리지 말 것
  물리 엔진, 보정 상수

확인할 것
  1. settings.forecast_steps는 이미 0..72h(3h 간격)로 잡혀 있다. 실제로 어디서 24h로 잘리는지 추적
  2. 강제장·경계가 72h까지 수집되는지 (NOMADS 응답 시간 포함)
  3. 실행 시간과 피크 메모리 (24h가 JAX로 4분이었다)
  4. GFS-Wave 대비 리드별 상관·편향·RMSE 곡선 — 24h에서 편향 +0.24 m로 단조 증가하던 것이
     72h에서 어떻게 되는지

완료 조건
  사이클 1개를 72h로 실행하고 리드별 skill 표를 docs에 기록.
  "해운에 쓸 수 있는 리드는 몇 시간까지인가"에 숫자로 답할 것.
  못 쓰는 구간이 있으면 그렇게 쓴다.

먼저 할 것
  실행 전에 예상 소요 시간과 디스크 사용량을 계산해서 보고할 것.
```
