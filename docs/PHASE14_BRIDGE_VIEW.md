# PHASE 14 — 선교 시점 (1인칭 해면)

작업 시점: 2026-08-26.

## 1. 무엇을 만들었나

예보 스펙트럼으로 실현한 해면을 배 위에서 보는 화면(`/bridge`).
지도 대시보드가 파고를 **위에서 색으로** 보여준다면, 이 화면은 그 파고가
실제로 **어떻게 보이는지**를 보여준다. 해운 판단에서 중요한 조우각을
같은 화면에서 읽을 수 있다.

## 2. 물리 — 장난감이 아니다

지난 작업으로 저장한 8변수가 그대로 재료가 된다.

```
m0        → 유의파고
m0/m1, √(m0/m2) → 평균 주기
a1, b1    → 평균 파향, 방향 확산
tp, dirp  → 첨두 성분
```

해면은 선형 중첩으로 만든다(`poseidon/physics/sea_surface.py`):

    η(x, y, t) = ΣΣ a_ij cos(k_i·x − ω_i t + φ_ij)
    a_ij = √(2 · E(f_i, θ_j) · Δf · Δθ)

E(f,θ)는 JONSWAP × cos^2s로 재구성한다. 확산 지수 s는 예보의 방향 확산에서
역산한다 — cos^2s 분포의 1차 모멘트가 r = s/(s+1)이고 Kuik의 확산이
σ_θ = √(2(1−r))이므로 **s = 2/σ_θ² − 1**이다.

근거: Longuet-Higgins (1963) *JFM* 17, 459–480 (가우시안 해면의 선형 중첩);
Longuet-Higgins, Cartwright & Smith (1963) (cos^2s 방향 분포);
Kuik, van Vledder & Holthuijsen (1988) *JPO* 18, 1020–1034 (방향 확산 정의).

### 2-2. 구현 중 잡은 결함 두 건

**각도 감싸기 누락.** cos^2s 분포에서 `cos(0.5·(θ−θ₀))`의 Δθ를 최단 각도로
감싸지 않아, 방향 격자를 평균파향에 정렬하자 **분포의 절반이 통째로 0으로
잘렸다.** 평균파향이 12.06° 계통적으로 틀어졌다. 이 프로젝트가 반복해 마주친
각도 처리 함정과 같은 구조다.

**WebGL uniform의 프로그램 바인딩.** uniform은 현재 활성 프로그램에만
설정된다. 하늘 셰이더를 추가한 뒤 성분 전달 함수가 하늘 프로그램이 활성인
상태에서 호출돼 **파 성분이 통째로 유실됐고 해면이 평평해졌다.**
증상이 "물리가 틀렸다"처럼 보였지만 원인은 렌더링 상태였다.

## 3. API

`GET /v1/seastate/point?lat&lon&cycle&lead&n_freq&n_dir&seed`

응답에 적률·성분 목록·규약·검증값이 들어간다. 성분은 진폭·파수·각주파수·
진행방향(수학각)·위상이다. 파수는 **유한수심 분산관계**로 푼다(ETOPO 수심 사용).

옛 예보(hs 단일 변수)에는 409를 반환한다 — 없는 것을 지어내지 않는다.

## 4. 정직성 장치 — 이 화면의 핵심

파면을 그럴듯하게 그리면 "실제 바다를 예측한 영상"으로 읽힌다. 그것을 막는다.

응답의 `provenance`가 항목별로 무엇이 검증됐는지 밝히고 화면에 그대로 표시된다.

| 항목 | 표기 |
|---|---|
| hs | 검증됨 — 실측 RMSE는 /v1/skill 참조 |
| 주기 | 부분 검증 — 9사이클·2026년 8월치만. Tm02 채점 표본 없음 |
| 파향 | 부분 검증 — 9사이클치만. 결함 관측소 3곳 제외 후 값 |
| 방향 확산 | **가정** — 리드 0에서는 초기장 cos² 유래(약 31.5°)이지 물리가 아니다. 채점된 적 없음 |
| 위상 | **예측 아님** — 시드 고정 난수. 개별 파의 위치·시각은 정보가 없다 |
| 해면 모델 | 선형 중첩. 파정이 실제보다 완만하다 |

추가로 **검증 범위 경고**를 파고에 따라 띄운다. 관측 최대 Hs가 3.2 m였으므로:
- Hs > 3.2 m → "검증 범위 밖 — 이 파고대는 채점된 적이 없다"
- Hs > 2.3 m → "검증 표본 희박 — Hs 2 m 이상 68건뿐"

기본 화면이 리드 36 h의 Hs 7.93 m 지점인 것은 의도적이다. **모델이 일상적으로
예측하는 대역의 대부분이 검증 범위 밖**이라는 사실(PHASE12 §3.3)을 눈으로
보여준다.

## 5. 조우각

파향(오는 쪽)과 선수방위에서 조우각을 계산해 나침반과 배지로 표시한다.

| 조우각 | 표시 |
|---|---|
| \|α\| ≤ 30° | 정면파 (head sea) |
| 60° ≤ \|α\| ≤ 120° | 횡파 (beam sea) — 횡동요 |
| \|α\| ≥ 150° | **선미파 — 서프라이딩·브로칭 주의역** |

IMO MSC.1/Circ.1228이 서프라이딩 위험으로 지목하는 것이 135° < α < 225°다.
다만 그 판정의 전제인 Hs > 0.04·L(선박 길이 함수)은 화면에 넣지 않았다 —
선박 제원을 받지 않기 때문이다. 이 화면은 위험을 판정하지 않고 **조건을
보여줄 뿐**이다.

## 6. 관찰 — 물리적으로 정확하면 밋밋해 보인다

구현 중 "파도가 안 보인다"는 문제를 오래 쫓았는데, 원인의 상당 부분이
버그가 아니라 물리였다. Tp 12.8 s 스웰은 파장 256 m이고 Hs 2.35 m면
**파장 대 파고가 약 300:1**이다. 실제 바다에서도 장주기 스웰은 완만하다.

가파르게 보이는 것은 짧은 주기의 풍파다 — 27.0N 128.5E의 Hs 5.66 m·Tp 7.6 s
(파형경사 0.063)가 화면에서 파정이 시선을 가릴 만큼 뚜렷하다.

**시각적 인상과 위험은 다르다.** 완만한 장주기 스웰이 선박에는 더 위험할 수
있다(파라메트릭 롤은 조우주기가 고유주기의 절반일 때 난다). 화면이 잔잔해
보인다고 안전한 것이 아니라는 점을 사용자가 오해하지 않도록, 수치 패널을
항상 함께 둔다.

## 7. 선박 (2026-08-26 추가)

`poseidon/physics/ship_response.py`. 화면에 갑판 실루엣이 생기고, 카메라가
선체와 함께 롤·피치·히브한다. 선체가 기울면 화면 전체가 기운다 — 실제
선교에서 보는 그대로다.

### 7-1. 무엇을 계산하는가 — 그리고 무엇을 계산하지 않는가

**계산하는 것: IMO MSC.1/Circ.1228 (2007)의 판정식.** 선장이 악천후에서
위험 상황을 피하도록 IMO가 제시한 지침이며, 선박 길이·속력·롤 고유주기와
파랑 조건만으로 판정한다. 근사가 아니라 지침 그대로다.

| 판정 | 조건 | 지침 |
|---|---|---|
| 높은 파고 | Hs > 0.04·L | §3.1 |
| 서프라이딩·브로칭 | 선미파(135°≤\|α\|≤180°) + V > 1.25√L kn | §3.3 |
| 동조 횡동요 | T_e ≈ T_R (±15%) | §3.2 |
| 파라메트릭 롤 | T_e ≈ T_R/2 | §3.4 |
| 파장 근접 | 0.8L ≤ λ ≤ 1.4L | §3.4 |

조우주기는 ω_e = ω − (ω²/g)·V·cos μ 로 푼다. 롤 고유주기는 지침의 근사식
T_R = 2CB/√GM, C = 0.373 + 0.023(B/d) − 0.043(L/100)을 쓴다.

**계산하지 않는 것: 유체역학 응답.** 실제 선체 응답은 선형 포텐셜 이론
(스트립 이론·패널법)으로 선체 형상에서 풀어야 하고, 그러려면 우리에게 없는
오프셋 데이터가 필요하다. 운동 추정은 1자유도 공진 근사이며
**절대 각도·변위는 신뢰할 수 없다.** 정성적 거동(공진 위치·대역폭)과
조건별 상대 크기만 의미가 있다.

### 7-2. 구현 중 드러난 모순 하나

처음 구현에서 **선미파 동조 횡동요를 경고하면서 롤 진폭은 0.0°로 표시**했다.
직접 횡강제를 `|sin α|`로 놓았는데 순수 정면·선미파에서 그 값이 0이기
때문이다. 물리적으로는 맞지만 화면에서는 "안전하다"로 읽힌다 — 그런데
바로 그 조건이 파라메트릭 롤 위험역이다.

두 가지로 고쳤다.
- 방향 확산 σ를 1차로 넣었다. 실제 바다는 방향이 퍼져 있어 순수 정면파에서도
  횡 강제가 0이 아니다. `beam = √(sin²α + (σ cos α)²)`.
- 파라메트릭 롤을 `parametric_risk`로 **분리**했다. 그것은 횡방향 직접 강제가
  아니라 종파에서 복원력(GM)이 주기적으로 변해 생기므로, 직접 롤 진폭에
  합산하면 안 된다. 두 값을 함께 내보내 오해를 막는다.

### 7-4. 남은 한계

## 9. 한계

- 선박이 없다. 시점만 있고 선체 운동(롤·피치·히브)은 계산하지 않는다.
  조우각은 보여주지만 **응답은 보여주지 않는다.**
- 선형 중첩이라 파정이 실제보다 완만하고 부서지지 않는다.
  Gerstner 파는 시각적으로 사실적이지만 스펙트럼과의 대응이 느슨해져
  도입하지 않았다.
- 성분을 96개로 자른다(진폭 큰 것 우선). 잘린 뒤 진폭을 되올려 m0는
  보존하므로 화면의 유의파고는 예보값과 일치한다.
- 방향 확산이 리드 0에서 사실상 상수라, 짧은 리드에서는 방향 분포가
  물리가 아니라 초기장 가정이다.

## 8. 2026-09-07 시각 점검 — 오진 기록

사용자 요청으로 8811 포트를 열어 중간 점검을 했다. 지도와 파고장이 전혀 그려지지
않아 앱 버그로 판단하고 다음을 순서대로 시도했다. **전부 헛수고였다.**

1. 베이스맵을 CARTO -> OSM 으로 교체
2. `setTimeout(markStyleReady, 2500)` 강제 개방
3. `isStyleLoaded()` 가드를 단 재시도 루프
4. 베이스맵을 초기 스타일에서 떼어내 사후 로드로 분리

실제 원인: **브라우저 패널이 숨김 상태(`document.hidden === true`)라
`requestAnimationFrame` 이 발화하지 않았다.** MapLibre 는 인라인 스타일이라도
첫 프레임을 rAF 위에서 처리하므로, rAF 가 죽으면 `style.load` 이벤트조차
끝나지 않는다. 이 상태에서 `map.getStyle()` 은 `undefined`, `isStyleLoaded()` 는
영원히 false 이고 **에러는 하나도 나지 않는다.**

증거:
- CARTO 타일 `200`, `/v1/field/hs.png` `200` (101,819 B), 모든 API `200`
- 캔버스 2560x1440, WebGL 컨텍스트 손실 없음, 워커 왕복 정상
- 최소 스타일(sources 비움 + background 한 장)로 새 Map 을 만들어도 동일하게 정지
- `styledata`/`sourcedata`/`error` 이벤트 **0건**
- `requestAnimationFrame` 콜백이 1.5초 안에 한 번도 호출되지 않음

rAF 를 `setTimeout` 으로 대체하자 즉시 `bg/base/hs` 세 레이어가 모두 붙고
정상 렌더됐다. 1~4번 변경은 되돌렸다. 검증용 셈은 확인 후 제거했다.

**교훈: 렌더가 안 보이면 앱을 고치기 전에 `document.hidden` 과 rAF 발화를
먼저 확인한다.** 에러가 하나도 없는 "조용한 정지"는 앱 버그보다 실행 환경을
의심할 신호다. `web/public/index.html` 지도 초기화부에 주석으로 남겼다.
