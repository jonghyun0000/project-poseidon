조사 대상 문서를 직접 내려받아 텍스트를 추출해 대조했다.

| 제품 | 벤더 | 화면의 주역 |

| SPOS 9.3.2 | ABB | INPUT(웨이포인트·기상한계·최적화목표) + ROUTING(항로 비교 테이블) 2화면 |

**정정**: BonVoyage System 은 DTN 이 아니라 StormGeo 계열이다. BVS 8.5 가이드 자체가
1차 증거다 — 표지·바닥글이 StormGeo 이고 지원 연락처가 전부 awtworldwide.com 이다.

### 공통 문법 네 가지

1. **산출물은 격자 파고 지도가 아니라 "계획 침로 위 시각별 조건"이다.**
   JTSB MA2024-02(ONE APUS)가 기술한 라우팅사 산출물은 침로 위 00·12 UTC 지점의
   풍향·풍속·파향·파고·파주기였다.
2. **파고 단독 표기는 결격이다.** IMO MSC.1/Circ.1228 의 어떤 판정도 파주기·파장·조우각
   없이는 성립하지 않는다. ONE APUS 는 파고 약 6 m 가 정상 예보돼 있었고, 침로를 20°
   바꿔 너울이 좌현 선미에서 좌현으로 옮겨간 것이 사고를 만들었다.
3. **기준시각·출처·면책을 화면에서 지우지 않는다.** SPOS 는 "항해 위험요소를 점검하지
   않았다"를 못박는다. NTSB MAR-17/01(El Faro)은 선교가 6시간 뒤처진 그래픽을 최신으로
   오인한 사고다.
4. **어느 제품도 자기 파고 예보의 검증 성적을 수치로 공개하지 않는다.**
   따라서 "상용 대비 몇 %"는 기준선 자체가 없어 어느 방향으로도 쓸 수 없다.
   동시에 이것이 우리가 유일하게 앞설 수 있는 축이다.

표시 문법의 참고 근거: IEC 62288:2021 §7.2.1.1(주·박명·야 3벌),
IMO MSC.191(79) 5.5.2·5.5.4(적색은 경보 전용, 점멸은 미확인 경보 전용),
IHO S-52 2.3.1g, S-411 12.1, WMO Code Table 3700.
**이 표준들은 형식승인 항해장비의 규범이고 우리 제품은 대상이 아니다.**
준수 의무가 아니라 참고 문법으로 쓴다.

## 5. 이번 작업 중 발견 — 리드 0 해상 셀 10.4% 영값

시간표를 시험하다 36.47N 129.47E 에서 `+0 h` 만 0.00 m 이고 `+3 h` 부터 2.02 m 인 것을 봤다.
서버가 직접 그렇게 응답한다(UI 버그 아님). 격자 전체를 세어 보니:

```
sea = np.nanmax(hs, axis=0) > 0.011      # 바다 셀 12,320개 (20260906T18)
lead idx 0: 바다인데 0인 셀 1278 (10.37%)
lead idx 1:                319 ( 2.59%)
lead idx 2:                 91 ( 0.74%)
lead idx 3:                 12 ( 0.10%)
lead idx 4:                  3 ( 0.02%)
```

`[가설 2026-09-07]` 초기장(GFS-Wave)의 바다 마스크와 우리 격자의 마스크가 어긋나
GFS-Wave 가 육지로 보는 셀에서 초기 hs 가 0 으로 들어가고 우리 물리가 약 12시간에 걸쳐 채운다.

**이것이 확인되면 PHASE17 과 직접 연결된다.** PHASE17 은 리드 0~6h 에 유의한 음의 편향
(-0.163 m)이 있고 이것이 GFS-Wave 로부터 상속된 것이며 리드 12h 에서 자체 물리가
교정한다고 기록했다. 영값 셀의 시간 감쇠가 그 편향의 시간 구조와 같은 모양이다.
검증 관측소는 연안에 몰려 있어 마스크 불일치의 영향을 가장 크게 받는 위치다.

**아직 검정하지 않았다.** 단일 사이클 관측이며, 이 프로젝트는 단일 사이클 지배로
네 번 틀린 이력이 있다. 별도 작업으로 분리했다.

화면 대응: `DRY_HS = 0.011`(서버가 육지·건조 판정에 쓰는 값과 동일) 이하를
'고요'가 아니라 **'값 없음 — 이 리드에 유효한 값이 없다'** 로 낸다.
0 을 '잔잔한 바다'로 읽히게 두지 않는다.

## 6. 오진 기록 — 숨김 탭 렌더 정지

작업 시작 전, 서버를 열어 중간 점검을 하는데 지도와 파고장이 전혀 그려지지 않았다.
앱 버그로 판단해 베이스맵 교체·강제 개방 타이머·재시도 루프·스타일 분리를 차례로 시도했다.
**전부 헛수고였다.**

실제 원인은 브라우저 패널이 숨김 상태(`document.hidden === true`)라
`requestAnimationFrame` 이 발화하지 않은 것이었다. MapLibre 는 인라인 스타일이라도
첫 프레임을 rAF 위에서 처리하므로 rAF 가 죽으면 `style.load` 조차 끝나지 않는다.
이때 `getStyle()` 은 `undefined`, `isStyleLoaded()` 는 영원히 false 이고
**에러는 하나도 나지 않는다.** 타일도 hs.png 도 API 도 전부 200 이었다.

상세는 PHASE14 §8. `web/public/index.html` 지도 초기화부에 주석으로 남겼다.

## 8. 이 재설계로도 여전히 벌어지는 격차

숨기지 않는다.

- **항로가 1급 객체가 아니다.** 어떤 엔드포인트도 좌표 배열을 받지 않는다.
  시간표는 "등록 지점 × 시각"이지 "항로 × 시각"이 아니고, 그 둘은 축소판 관계가 아니다.
  14 kn 선박은 12시간에 약 168 nm(2.8°) 이동해 L1 격자 11칸을 지나간다.
  **고정 지점의 시계열은 정박선의 시계열이다.** 이 문장을 시간표 머리에 적었다.
- **예보 지평 72 h.** 상용 라우팅의 결정 지평은 5~10일이다. 72 h 는 결정이 끝난 뒤의 전술 창이다.
- 속력손실·저항 증가·ETA·연료가 없다. 용선주가 보는 것은 파고가 아니라 도착시각과 연료다.
- 해류가 없다. 대한해협·쿠로시오가 도메인 한복판인데 파-해류 상호작용이 미결합이다.
- 앙상블이 없다. 결정론 1멤버이므로 초과확률이 없고, 편출 결정은 본질적으로 확률 판단이다.
- **검증이 판단이 필요 없는 조건에서만 이뤄졌다.** 2026-09-07 기준 관측 최대 Hs 4.2 m,
  p95 2.356 m. 해운 판단이 결정적인 4 m 이상·겨울 계절풍·태풍 통과 표본이 사실상 0건이다.
- 주기·파향은 부분 검증, Tm02 는 원리적으로 채점 불가.
- 인증·CORS·레이트리밋이 없는 로컬 단일 사용자 전제다.
